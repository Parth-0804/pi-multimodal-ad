# Automation readiness — proposal only

No controller has been installed, built, started or scheduled. TASK_QUEUE.json is a proposal and RUN_STATE.json is editable state; neither is enforcement. Local CLI invocation and JSON creation were observed; a Codex executable path exists but noninteractive execution/schema features were not invoked. Network usability, remote jobs, service credentials and restart automation are UNKNOWN and unused. The sandbox's loopback setup failed; approval-mediated fallback allowed this audit, which does not justify unrestricted future execution. Installed package versions were read from metadata without imports, so runtime compatibility remains UNKNOWN.

Smallest later controller proposal: one local foreground coordinator, a durable versioned task ledger, an append-only attempted-command/event log, one writer lock, a protected human approval record, a constrained command launcher, and a separate read-only evidence-review stage. No web app, cloud orchestration or new service is required to write this plan. Installing/implementing/testing any controller requires a separate approved code/config scope.

Persistent state records immutable task IDs, parent/dependency IDs, protocol/code/config/data fingerprints, expected outputs, command allowlist, resource reservation/actual usage, status/attempt timestamps, reviewed evidence and blockers. Atomic state updates and immutable attempt directories preserve completed work. On resume compare hashes/status with artifacts, check for an existing process/lock and validate last durable checkpoint. Never infer completion from a status string. Do not launch the historical supervisor or wait on Task4 as a way to resume it.

Dependencies follow the copied queue: literature -> approved protocol -> separately approved controller setup -> approved baseline checks -> only missing controlled robustness -> optional selected encoder studies/dispositions -> METHOD_FREEZE -> external assessment; UI remains optional. The controller must enforce selected optional-study dependencies explicitly, since a static queue edge to ROBUSTNESS alone does not prove all selected studies have a disposition. Literature execution requires context/file isolation before launch, independently of experiment approval.

Approval protection must be outside implementation/reviewer write permissions. A human-owned record binds task, exact protocol/source/config/data identity, allowed commands/paths/services, exclusions, review policy and hard numeric budgets. The launcher validates it immediately before each action. No agent-writable status, reviewer verdict or elapsed time can unlock a stage. Single writer serialization is enforced by an OS lock and narrow output-directory permissions, not merely a prompt. Review outputs are findings; the coordinator is the only report writer. Reviewer should receive read-only source/report mounts and no experiment execution capability; current shared-filesystem agents provide a separate context but read-only behaviour is instruction-based, not a proven OS restriction.

Least privilege: scientific source/config/raw/historical trees read-only; approved new run directory writable; deny credential paths; no unnecessary network or remote compute; permit only commands/inputs named by the approved task. Even a static reader must not execute project imports or deserialize model files without a later explicit scope. Preserve dirty/untracked inputs in a hashed snapshot/manifest under approved paths before future runs; never reset/stash/clean a researcher's workspace.

Hard limits TO SET by user: model/API spend, permitted model/service, GPU/CPU/device time, wall time, storage/free-space reserve, trials/seeds/realizations, workers/concurrency, downloads and retry count. Missing values block execution; null historical wall-time is not an unlimited budget. Launcher enforces wall time/process-group termination and storage/resource accounting outside agent-generated scripts. Bounded retries must be reserved from budget and limited to explicitly retryable technical faults; validity failures, permission rejection or protocol drift do not trigger autonomous scientific fixes. No retry policy numbers selected in this audit.

Stop/resume/failure: log attempt before launch; mark RUNNING with owner/lease; flush state before pause/failure and after artifacts close. Interruptions preserve inputs, completed outputs and checkpoints. Expired leases or process mismatch require reconciliation, not duplicate jobs. A failed dependency blocks its descendants, while unrelated authorized work may continue. Stop on source/data/approval drift, duplicate writers, secret exposure, budget exhaustion, unavailable required review, unsupported runtime or Task4 overlap. A valid negative result is DONE scientifically and does not trigger search for a positive replacement.

Later fail-closed dry-run checks must demonstrate no launch with absent/altered approval, rejected path/command, exceeded budget, failed reviewer gate, excluded task, stale checkpoint or interrupted owner. Those controller checks are not performed now: user prohibits tests and implementation in this task. Audit report consistency checks are document/metadata checks only.

Results-blind literature isolation: spawn_agent(fork_turns=none) can omit chat history, but agents share this repository and tools. That does not prevent access to outcome files. A separate workspace/mount or explicit access allowlist with no project outcomes must be established by the host before labelling a later review results-blind. Current coordinator and audit reviewer are not literature reviewers; no blind literature task was launched. If isolation is unavailable, disclose NOT RESULTS-BLIND and obtain a revised scope decision before execution.

Evidence checked: actual exposed shell/collaboration tool definitions, observed shell and metadata behaviour, copied queue and inspected historical source entry points.
Still uncertain: enforceable fresh-context filesystem isolation, protected approval mechanism, runtime tests, CLI schema/controller support and all budgets.
Defensible conclusion: audit handoffs can be coordinated in-session; unattended research is not technically ready or approved.
