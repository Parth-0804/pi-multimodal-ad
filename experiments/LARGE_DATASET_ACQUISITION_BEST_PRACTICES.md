# Large Research Dataset Acquisition — Lessons Learned & Best Practices

## Context

This document summarizes the practical lessons learned while downloading and preparing the **PHM North America 2026 Data Challenge** dataset.

Although the examples originated from the PHM dataset, the principles are intended to be reusable for other large industrial, scientific, multimodal, or cloud-hosted datasets.

The most important lesson is:

> **Data acquisition is part of the scientific methodology.**
>
> A dataset that is incomplete, duplicated, corrupted, wrongly authenticated, or misunderstood at schema level can lead to incorrect analysis and false scientific conclusions.

---

# 1. A Successful HTTP Response Does Not Mean the Dataset Was Downloaded

## What happened

An early downloader appeared to work successfully and returned HTTP status `200`, but the resulting files were effectively empty compared with the expected multi-gigabyte archives.

The server had returned a small JSON/HTML response rather than the actual ZIP archive.

## Lesson

`HTTP 200` only means:

> The server responded successfully.

It does **not** mean:

> The expected dataset file was returned.

## Best practice

Validate the response before trusting it.

Check at least:

- HTTP status
- `Content-Type`
- `Content-Disposition`
- `Content-Length`
- `Content-Range`
- expected approximate file size
- file signature / magic bytes

For a ZIP archive, for example:

```text
Expected:
Content-Type → application/octet-stream
File signature → PK
Expected size → multi-GB

Not sufficient:
HTTP 200 → success
```

# 2. Browser Download URLs May Depend on Session State

## What happened

The dataset could be downloaded successfully in Chrome, but simply copying the download URL to the Linux VM did not work.

The Synology File Station request also relied on:

```text
sharing_sid
```

which was stored as a session cookie.

The actual request therefore depended on more than just the visible URL.

## Lesson

A browser download link may rely on:

- cookies
- temporary session IDs
- signed URLs
- authentication headers
- referer headers
- redirects
- JavaScript-generated request parameters

## Best practice

When a download works in the browser but not in a script:

1. Open browser Developer Tools.
2. Open the **Network** tab.
3. Trigger the real download.
4. Inspect the successful request.
5. Record:
   - Request URL
   - Cookies
   - Request headers
   - Response headers
   - Redirect behaviour
   - Authentication/session parameters

Avoid guessing undocumented endpoints before inspecting the working browser request.

# 3. Let the Download Machine Establish Its Own Session

## What happened

A `sharing_sid` generated by the Windows browser was copied to the remote Linux VM.

The VM still received a JSON response rather than the real ZIP.

The working solution was for the VM itself to open the public share page and create its own Synology session.

## Best practice

Prefer:

```text
Machine performing the download
        ↓
creates its own authentication/session
        ↓
downloads using that session
```

instead of:

```text
Browser on another computer
        ↓
copy token/cookie
        ↓
remote download machine
```

This is especially important for temporary cookies, expiring tokens, cloud portals, authenticated research repositories, signed download links, and SSO-based systems.

# 4. Probe Large Files Before Downloading Them

## What happened

Instead of immediately downloading a ~20 GB file, the robust downloader first requested a tiny byte range.

Example:

```text
Range: bytes=0-0
```

A valid server response can reveal:

```text
HTTP 206 Partial Content
Content-Range: bytes 0-0/TOTAL_FILE_SIZE
```

This confirmed:

- authentication worked
- the requested file existed
- the response was the real binary file
- the expected total size was known
- range requests were supported

## Best practice

For very large files, use:

```text
AUTHENTICATE
    ↓
PROBE
    ↓
VALIDATE HEADERS
    ↓
DOWNLOAD
```

instead of:

```text
AUTHENTICATE
    ↓
DOWNLOAD 20 GB
    ↓
discover later that the response was wrong
```

---

# 5. Large Downloads Must Be Resumable

Large archives may fail because of network interruptions, expired sessions, VPN disconnects, server resets, machine restarts, or terminal closure.

Restarting a 20 GB file from zero after every interruption is inefficient.

Use temporary partial files such as:

```text
dataset.zip.part
```

Then:

```text
dataset.zip.part
        ↓
download / resume
        ↓
validate exact size
        ↓
validate file signature
        ↓
dataset.zip
```

Do not give an incomplete file its final filename.

---

# 6. Handle Resume Responses Carefully

When resuming, the client may request:

```text
Range: bytes=<current_size>-
```

A correct resume response is normally:

```text
206 Partial Content
```

Some servers may ignore the range and return:

```text
200 OK
```

with the entire file.

Blindly appending that full response to an existing `.part` file can corrupt the archive.

## Best practice

```text
206 → safe resume / append
200 → server may have ignored Range; restart safely
4xx / 5xx → fail and refresh authentication/session
```

---

# 7. Refresh Authentication Separately from Retry Logic

A long-running download may outlive the authentication/session lifetime.

Retrying the same request with an expired token is not a meaningful retry.

A better design is:

```text
Download fails
      ↓
preserve .part file
      ↓
create fresh session
      ↓
retry / resume
```

Keep network retry logic separate from authentication refresh logic.

---

# 8. Validate the File After Download

A file existing on disk does not prove that it is correct.

Recommended checks:

1. Expected size
2. File signature
3. Archive integrity
4. Checksum where available

For ZIP files:

```bash
unzip -t dataset.zip
```

Recommended validation hierarchy:

```text
1. Expected filename
2. Expected approximate/exact size
3. Content-Type
4. File magic/signature
5. Archive integrity
6. Cryptographic checksum
```

---

# 9. Plan Storage Before Downloading

Large datasets consume more space than the raw archive size alone.

Storage may be required for:

```text
compressed raw dataset
+
temporary extraction
+
processed/intermediate files
+
EDA outputs
+
model checkpoints
+
logs
+
safety margin
```

Before starting:

```bash
df -h
du -sh <dataset-folder>
```

A useful rule is to keep approximately **20–30% disk capacity free** during heavy processing.

---

# 10. Avoid Full Extraction of Huge Archives When Possible

Instead of permanently extracting every large ZIP, process one archive member at a time:

```text
ZIP archive
    ↓
read one HDF5 member
    ↓
temporary file
    ↓
extract required features
    ↓
delete temporary HDF5
    ↓
process next member
```

Prefer streaming, temporary extraction, member-by-member processing, or lazy loading.

---

# 11. Never Assume Archive Structure from the Filename

A file named:

```text
Exp-A_HDF5_LF.zip
```

did not directly contain HDF5 files.

The actual structure was:

```text
Exp-A_HDF5_LF.zip
│
├── Exp-A_HDF5_Run-1_LF.zip
├── Exp-A_HDF5_Run-2_LF.zip
├── Exp-A_HDF5_Run-3_LF.zip
├── Exp-A_HDF5_Run-4_LF.zip
└── Exp-A_HDF5_Run-5_LF.zip
        ↓
      HDF5 files
```

## Best practice

Inspect first:

```bash
unzip -l dataset.zip | head -100
```

Use:

```text
Inspect archive
      ↓
understand nesting
      ↓
design loader
```

---

# 12. Never Assume Schema Consistency Across Files

Some EXP-A HDF5 files used:

```text
/CI/FM4
/CI/NA4
/CI/M6A
/CI/ALR
```

while others used:

```text
/CI_4s/FM4
/CI_4s/NA4
/CI_4s/M6A
/CI_4s/ALR
```

## Best practice

Generate a schema inventory before large-scale analysis:

```text
file
dataset path
shape
dtype
sampling rate
missing?
```

Then use robust candidate mappings.

---

# 13. Dataset Quality Problems Can Matter More Than Modelling

EXP-A Run-2 contains substantial overlap with Run-1.

For the initial high-frequency EDA, Run-2 was therefore intentionally excluded from the lifecycle sample:

```text
Run-1 → Run-3 → Run-5
```

Before modelling, investigate:

- exact duplicates
- near-duplicates
- missing files
- missing channels
- corrupted samples
- unexpectedly short runs
- metadata inconsistencies
- provider warnings

A sophisticated model cannot compensate for contaminated experimental design.

---

# 14. Smoke-Test Before Scaling

Implementation problems are much cheaper to discover on a few files than on hundreds of HDF5 files.

Recommended scale-up:

```text
1 file
  ↓
3 files
  ↓
1 run
  ↓
multiple runs
  ↓
full dataset
```

Example:

```bash
python eda_script.py --max-files-per-run 3
```

Only run full-scale analysis after the smoke test succeeds.

---

# 15. Separate Ingestion, Validation and Analysis

Avoid one giant script that performs everything.

Prefer independent stages:

```text
01_DOWNLOAD
      ↓
02_VALIDATE
      ↓
03_INSPECT
      ↓
04_PREPROCESS
      ↓
05_BASIC_EDA
      ↓
06_ADVANCED_EDA
      ↓
07_MODEL
```

Each stage should be restartable independently.

---

# 16. Preserve Provenance

For research work, preserve enough information to reproduce how the dataset was acquired.

Recommended metadata:

```text
Dataset name
Dataset version
Source URL
Download date
Original filenames
Expected file sizes
Checksums
Known provider issues
Downloader script version
Authentication method
Preprocessing version
Experiment selection rationale
```

# Recommended Workflow for Future Large Datasets

```text
1. READ DOCUMENTATION
        ↓
Understand experiments, modalities, known issues and expected sizes

2. INVENTORY BEFORE DOWNLOAD
        ↓
Determine what files actually exist and which ones are required

3. PLAN STORAGE
        ↓
Raw + temporary + processed + safety margin

4. TEST ACCESS
        ↓
Ensure the download machine can establish its own session

5. PROBE ONE FILE
        ↓
Check HTTP status, Content-Type, filename and expected size

6. DOWNLOAD ONE REPRESENTATIVE FILE
        ↓
Confirm the actual binary content

7. VALIDATE
        ↓
Size + signature + archive integrity + checksum

8. IMPLEMENT RESUMABLE DOWNLOAD
        ↓
.part files + Range requests + retries + session refresh

9. SCALE DOWNLOAD
        ↓
Download sequentially with logging and progress tracking

10. INVENTORY DOWNLOADED DATA
        ↓
Inspect archives, nesting, HDF5 schema and missing channels

11. CHECK DATA QUALITY
        ↓
Duplicates + missing data + corrupted files + provider warnings

12. SMOKE-TEST PROCESSING
        ↓
Process 1–3 representative files

13. SCALE EDA
        ↓
Run-level → experiment-level → full dataset

14. PRESERVE PROVENANCE
        ↓
Document source, versions, scripts, checksums and known issues
```

# Practical Pre-Download Checklist

- [ ] Read the official dataset documentation.
- [ ] Identify all available experiments/runs.
- [ ] Record expected archive sizes.
- [ ] Check known data-quality issues.
- [ ] Check available storage.
- [ ] Confirm the download machine can authenticate.
- [ ] Probe one file before downloading the full archive.
- [ ] Confirm binary response rather than JSON/HTML.
- [ ] Use resumable `.part` downloads.
- [ ] Refresh sessions automatically when necessary.
- [ ] Validate exact final file size.
- [ ] Validate archive signature/integrity.
- [ ] Generate an archive inventory.
- [ ] Inspect HDF5/file schema before coding loaders.
- [ ] Check duplicates and missing channels.
- [ ] Smoke-test the processing pipeline.
- [ ] Scale only after validation succeeds.
- [ ] Preserve acquisition and preprocessing provenance.

# Key Principles

> **Never trust a file because the download command completed successfully. Validate the content.**

> **Do not design the analysis pipeline until the physical file and schema structure is understood.**

> **For large datasets, resumability and restartability are requirements, not optional features.**

> **Dataset-quality checks should happen before modelling.**

> **Robust data engineering is part of the scientific method.**

An ingestion error can propagate as:

```text
Wrong authentication
        ↓
Wrong server response
        ↓
Wrong/incomplete file
        ↓
Incorrect preprocessing
        ↓
Incorrect EDA
        ↓
Incorrect scientific interpretation
```

A robust workflow instead follows:

```text
Authenticate
     ↓
Probe
     ↓
Validate
     ↓
Download / Resume
     ↓
Validate again
     ↓
Inspect structure
     ↓
Check data quality
     ↓
Smoke-test
     ↓
Analyse
```

---

# Final Takeaway

The PHM dataset download process demonstrated that **acquiring a large industrial dataset correctly is itself a data-engineering task**.

The best general workflow is:

> **Validate → Inspect → Smoke-Test → Scale → Preserve Provenance**

Only after those steps should the dataset be trusted for scientific analysis or machine-learning development.
